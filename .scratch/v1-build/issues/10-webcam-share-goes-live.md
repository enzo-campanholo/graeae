# 10: Webcam share goes live

**What to build:** A member presses "Share webcam" and their webcam share is live at once: every present member's bar shows the webcam icon on their row, and the sharer sees a small preview at the foot of the bar with a stop button. Pressing stop ends it for everyone.

This ticket introduces the media layer seam and builds everything against fakes. The real media server arrives in ticket 12.

Spec: [Modules](../spec.md#modules), [Media connections and records](../spec.md#media-connections-and-records), [Checks on every request](../spec.md#checks-on-every-request), [Shares](../spec.md#shares), [Relay](../spec.md#relay). ADR 0003.

UI: build with the impeccable skill, following `DESIGN.md`.

Blocked by: 05, 08

Status: resolved

- [x] The media layer is one seam between the instance and the media server. This ticket defines only the operations it uses: make a media connection, publish a share's tracks, force-close named tracks, mint a relay credential. Tickets 11, 17 and 21 add pull, change of quality and the listing of a connection's tracks
- [x] An in-memory fake media server implements it for Seam 1: it keeps tracks per media connection, lets a test read them, and can be told by a test to fail or delay a call, through a control that exists only in tests. Its state lives outside the instance, so it outlives a restart of the instance
- [x] The media client is the browser's one module for capture and the tab's media connection, with a fake for Seam 2 that captures and connects nothing
- [x] A tab makes its one media connection the first time it shares or watches, not on opening the room
- [x] A relay credential lasting 12 hours is minted for each new media connection and handed to that tab; the backend keeps no record of it
- [x] The browser never receives or sends a media server identifier
- [x] The backend picks every track name and writes the media connection and share records to storage before calling the media layer
- [x] To share, the backend checks: a remembered device, access to the room, this tab present in that room, and no other live webcam share by the member (a second attempt is refused until ticket 19 adds hand-over)
- [x] A share is live once registered with the media server; every present member's bar shows its icon at that moment, and the list of rooms shows its count of live shares
- [x] "Share webcam" starts with no dialog: 1 click
- [x] The sharer's preview and stop button sit at the foot of the bar
- [x] Stop and a clean leave both end the share by a forced close; the record is dropped only after the close returns
- [x] Seam 1 tests assert on socket messages and on the fake's tracks; a Seam 2 journey with two browsers

## Comments

**Done** on `ticket/10-webcam-share-goes-live`. `pnpm test` (Seam 1, then Seam 2), `pnpm typecheck` and `pnpm lint` pass. Migration `0004-media-connections-and-shares.sql` (renumbered after ticket 07's 0003), tested on an instance set up on 0001 to 0003 (`test/migrations.test.ts`).

- **The media layer** is `src/instance/media/layer.ts`: `connect()` gives the media server's id for a new media connection, `publish(connection, offer, tracks)` gives the SDP answer, `close(connection, tracks)` is the forced close, and `relayCredential(ttlSeconds)` gives `iceServers`. A `Track` is `{ name, mid }`: the instance picks the name, the browser's transceiver gives the mid, and Cloudflare closes by mid. `src/instance/media/index.ts` (`mediaLayer(env)`) returns the fake today. **Ticket 12** adds the Cloudflare implementation there and the switch; ticket 11 adds `pull`, 17 quality, and 21 the listing.
- **The fake** (`src/instance/media/fake.ts`) keeps its state in the module, so it outlives `instance.restart()`. The instance only sees `fakeMediaServer: MediaLayer`. Tests use `fakeMediaControl`, which the harness hands out as `instance.media`: `connections()` (each connection's open tracks), `credentials()` (with the ttl asked for), `identifiers()` (every id and track name handed out), `fail(op)` and `hold(op)` (`{ reached, release }`, optionally `{ fail: true }`). The harness resets it at `startInstance`. A held call and the test run in different I/O contexts, which cannot share a promise (workerd crashes or refuses the I/O), so a hold is a flag each side polls on its own timers.
- **Protocol.** A new `media` area (`src/shared/socket/media.ts`) is the tab's own conversation about its media connection, sent to that tab alone and outside `RoomView`. A tab sends `media.connect` and gets `connected { iceServers }` or `unavailable`; a second `connect` gets no answer. The shares area now has `SharesState { live: LiveShare[] }` (`{ member, kind }`), changes `started` and `ended` to the whole room, and requests `start { kind: "webcam", offer, video }` (video is the mid) and `stop { kind }`. The answer to a start goes to that tab alone, as `media.published { kind, answer }` or `media.refused { kind }`. `ShareKind` moved to `src/shared/socket/shares.ts`; `src/app/lib/share.ts` re-exports it. `ListedRoom` gained `live`, the count of live shares, and `relist` runs when a share starts or ends.
- **Records.** `media_connection` is keyed by the tab's socket id (sockets now also carry a `tab:<id>` tag; `Signaling.toTab` and `isOpen`), with device, room and the media server's id, which is null until the media server answers. `share` has member, device, room, tab, kind, its video track's name and mid, room for an audio track (ticket 15), and `live_at`, null until publish returns. No foreign keys to `device` or `member`, so forgetting or removal (tickets 07, 09, 20) is not blocked by them. `src/instance/shares.ts` holds the rules. Each start, publish, close and leave first writes or keeps the record, then calls the media layer, and drops the record only once the close returns.
- **Checks on a start**, in `Instance.request`: the device is still remembered (`People.deviceMember`) and still the tab's member, the member still has access to the tab's room, the tab is present (its socket is open on that room), the tab's media connection is made, and the member has no other webcam share record anywhere in the instance, live or still starting. The device check is tested by using the setup secret again with a tab open. **The access check is untested**: nothing takes access away yet. **Ticket 09** should add a test that a member removed from a room is refused a start from a tab still open there.
- **Decisions.** A share is shown as ended only once its forced close returns. If the close fails, the share stays live in the room and the record stays, so a new webcam share is refused until **ticket 21** retries the close. A start whose publish fails force-closes the named track before dropping the record. A tab that leaves while publish is still under way gets its track closed as soon as publish returns, and nobody hears it start. A restart leaves shares live in storage. The restart cuts the tabs' sockets, and the new instance never hears those tabs leave, so the shares stay listed until **tickets 06 and 21** (grace period, sweep after restart) deal with them.
- **The media client** (`src/app/lib/media/`): `captureWebcam`, `connect(iceServers)`, `offer(capture)` (gives `{ sdp, video }`), `accept(answer)`, `stop(capture)`, `close()`. Only `FakeMediaClient` exists, which captures nothing (its stream is null) and makes a stand-in offer with a new mid per capture. `createMediaClient()` returns it today, and in production too, until **ticket 12** adds the real one and the switch. The room client carries the conversation: `shareWebcam()` (capture, the connection the first time, offer, answer) and `stop(kind)`, and it keeps `mine`, this tab's own shares (starting, live, stopping). A `shares.ended` for your own share makes the tab stop its capture and drop it, whatever ended it.
- **The page.** "Share webcam" starts at once with no dialog. It reads "Starting" while starting and "Webcam live" (disabled) while a webcam of yours is live from any tab or device. That avoids the refusal a second share would get, until ticket 19's hand-over. The foot shows this tab's live shares as `OwnShare` with `SharePreview`: the local video, mirrored for a webcam, or the kind's icon faintly on the letterbox when there is no picture (the fake). Stop disables itself while the close runs. A refused or failed start shows "Your webcam didn't start. Try again." above the buttons. A sharer's row shows the webcam icon for everyone else, and the rail brightens a sharer's initial. Your own row shows no icon: watching your own share from another device is **ticket 11**'s. Clicking the icon does nothing yet (ticket 11). `StageEmpty` hides "Watch everything" until it has a handler, so the stage says "Click a name to watch what they share." when others have something live. The list of rooms shows each room's real live count.
- **Merged with ticket 07.** `Signaling.closeDevice` now returns the room tabs it cut off, and forgetting a device ends their shares by the same forced close as a clean leave (tested in `test/shares.test.ts`). It runs in the order the cut-off asks for: storage first, then closes, then the room is told. **Ticket 20** folds this into the one cut-off routine. `test/you.test.ts` gained `live: 0` in its list line.
- **Seam 2:** `test/browser/shares.spec.ts` (member Iara), in the default project: one click to share, the preview and "No one watching", the icon on the owner's bar, Stop, then sharing again and closing the tab. Under load from another agent's tests on the same machine, Seam 2 journeys sometimes timed out at the invite's join, in a different journey each time. They passed when re-run.
