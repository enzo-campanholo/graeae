**What to build:** graeae counts usage, and the owner sees it on the owner page: GB used this month, the usage budget and the projected month-end figure, with a small meter in the owner page's navigation. The owner sets the day of the month on which usage resets.

Spec: [Usage and the usage budget](../spec.md#usage-and-the-usage-budget), [Other pages](../spec.md#other-pages) (Usage).

- **The count** (`src/instance/usage.ts`). A `usage.received { bytes, relayed, final? }` request carries the running total the tab's media connection's transport has received since it opened. The difference from the tab's last total is charged (`usage_tab`), so the first report is charged in full and a lost one is made up by the next. A `final` total, or a total lower than the last (a restart whose final was lost), makes the next count from zero. Every reported byte gets `SAFETY_MARGIN_PERCENT` (5) on top, a constant. `RELAYED_COUNTS_TWICE` is the one switch for the doubling: it doubles a relayed report and a gap after one. Charges go to the UTC day they are made on (`usage_day`), so moving the reset day recounts nothing. The watching hooks (`began`, `ended` on `WatchingListener`) record each watch with its share's maximum bitrate (`usage_watch`). A watch that ends while its tab can still report waits for that tab's next total. One whose tab is gone (grace period run out, cut off, left) is charged from the later of its start and the tab's last report until the instance recorded it as ended, at 12, 6 or 1.5 Mbps. A sharer's tab reports only what it receives, so an upload is never counted.
- **The month** runs from the owner's day at midnight UTC to the same day of the next month; a month without that day resets on its last day. `GET /api/owner/usage` gives `used`, `budget` (1,000 GB, `USAGE_BUDGET_BYTES`, for ticket 24 to make settable), `projected` (the month so far at the same daily rate, with the first day counted whole so the first hours do not project a wild figure, and never below `used`), `resetDay`, `since` and `until`. `PUT /api/owner/usage/reset-day { day }` takes 1 to 31. Settings live in a new `setting` table (name, integer value), which ticket 24 can use for the budget. Both addresses are the owner's alone, so members see nothing.
- **The tab's reports** (`room-client.svelte.ts`). Every 5 seconds (`USAGE_REPORT_EVERY_MS`, on the worker-driven `every` so a hidden tab keeps reporting) once its media connection is made, until it is let go of. `transport.ts` reads `getStats()`: Chromium's `transport` entry, or Firefox's candidate pairs summed, and the relay from the local candidate of the pair in use. Reports go out in the order they were read. **On `media.dropped`** (ticket 22) the tab reads its total before letting the connection go and sends it as `final`. **After the grace period ran out** it sends none: the instance has charged that connection's watches already and the tab is a new one there. **Decision:** a report goes out only once the socket has brought the room's state. `Connection.send` queues messages while a socket opens (ticket 22), so without that check a report queued during a long drop would reach the new tab and be charged in full a second time.
- **The page** (impeccable skill, following `DESIGN.md`). `OwnerUsage` holds the figures for the whole owner page. It asks only once `/api/me` says this is the owner, again every 15 seconds while the page is in view, and on coming back into view. The navigation's meter reads it in place of the sample. The Usage section shows "Used", "Usage budget" and "Projected by the month's end" as three figures over the full-width track, with a faint stretch of fill out to the projection. The projection turns amber with a line ("At this rate the usage budget runs out before the month ends.") once it passes the budget. A line says the budget bounds what members watch, not the whole Cloudflare bill, and that 5% is added. The reset day is a number field with Save, "Next reset 1 December, at midnight UTC." and a line on matching it to the Cloudflare billing date. Gigabytes read to a tenth under 10 GB ("0.4 GB"). `GIGABYTE` moved to `src/shared/api.ts`, and `putJson` joined `api.ts`. Screenshots (dark and light) come from `GRAEAE_SCREENSHOTS=<dir>` on the meter journey.

- *The usage comparison* failed with 5%: +13.3%, outside 0 to 10%. The browser's own total already reads +7.9% above the media server's egress, since its transport counts SRTP, RTCP and ICE overhead that Cloudflare's per-track figure leaves out. **Decision (owner):** `SAFETY_MARGIN_PERCENT` is 0, which puts the same session at +7.9%. The margin applies linearly to the same reports, so no second session was run. The tests, the Usage section's line, the README's Cost section (ticket 26's open point) and the spec now say so.
- *Relayed watching* (box 6) holds. With UDP from Chrome blocked by a Windows firewall rule, the dump's selected pair had a local candidate with `candidateType: relay`, through `turn.cloudflare.com:3478` over TCP. graeae's count rose by 2.1 × 1.3566 GB, which matches the transport's total, so `transport.ts` saw the relay on a real connection and the report said `relayed: true`. Packet loss was 0.1%.
- *Doubling.* Cloudflare's pricing page says traffic between the relay and the media server "is not charged twice". On this TCP relay, though, the media server's egress read 16% above what the browser received, while the relay's read about 1% above. So counting relayed watching once would read below the bill if Cloudflare bills the media server's figure. **Decision (owner):** `RELAYED_COUNTS_TWICE` stays `true` for now. **Still open, as a box on ticket 27:** read Cloudflare's Billable Usage for 2026-11-17 once it posts. If the relayed session was billed at the relay's figure (about 1.39 GB rather than 1.59 GB), counting once is safe and the switch can go to `false`. The spec's Verification paragraph records the outcome.
