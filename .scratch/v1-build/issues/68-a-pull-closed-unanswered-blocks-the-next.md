# 68: A pull closed without its offer reaching the tab blocks that connection's next pull

Status: resolved

Blocked by: none

**What was seen:** ticket 67, on `graeae-test` (2026-11-24). A replacement's pull returned after its share had gone. The instance force-closed it without sending its offer to the tab. 5 s later the next pull into the same session got `406 The current signaling state is expecting a remote answer: renegotiation is expected`. The media server takes no other pull into a session until the browser answers the last offer, and closing the pulled track does not change that (`docs/media-server.md`). Ticket 67 fixed this for a replacement's steps only.

**Why (from reading the code, not seen yet):** these places still close a returned pull without sending its offer. Each keeps the tab's receiving connection, so that connection's next pull should then fail with 406, and the watch that asked for it is refused or leaves the stage.

- `Shares.watch`: the share ends, or the tab's socket closes, while the media server makes the pull. A tab in its grace period comes back to the same connection. If the connection carries another watch, it is kept and not forgotten.
- `Shares.move`: the new share ends, or the watcher's socket closes, while its pull is made (`!connected || gone(to)`). A pull returning to a connection that has been replaced meanwhile is harmless, since that session takes no pull again.
- After a restart: a pull the media server made just as the instance stopped is closed by the sweep (`test/restart.test.ts`, "closes a pull the media server made just as the instance stopped"). The tab keeps its receiving connection, and its next watch pulls into the same session. That test fails under the fake's `oneOfferAtATime()`.

**What to decide:** whether to send each such offer to the tab anyway (as 67 does: `pulled` or `moved`, answered, then closed), or to let go of the connection so the tab's next watch makes a new one. Check on real media first, e.g. a `repro-68.ts` that ends a share while a watch of it is being pulled onto a connection that carries another watch. Seam 1 can show each case with `oneOfferAtATime()` and a `hold("pull", { done: true })`.

**Implementation (2026-11-26): fixed, and checked on `graeae-test`.**

How it works:

- `Shares.block` records the tab's current receiving connection as blocked. It is keyed in the instance's storage next to `unanswered`, so no migration is needed. It is called where a returned pull is closed unanswered:
  - `watch`: the share ended, the tab left, or the connection was replaced meanwhile.
  - `move`: the new share ended, the tab left, or the receiving target changed.
  - The sweep of a half-made pull after a restart.
- The block is cleared when the connection is forgotten (`forgetIfEmpty`) or replaced (`finishReplacement`).
- `Shares.watch` on a blocked connection asks the media server nothing and returns `{ watching: false, blocked: true }`. The instance then:
  - lets go of the connection if it carries nothing (`dropped`, as with 66);
  - answers `pull-refused` with `blocked: true`.
- The tab drives the replacement. It does not start on its own, so it keeps 64's final usage total, the `replacements` count and the negotiation turn. Inside the watch's own turn, the room client:
  - runs the replacement (`media.replace`, `why: "blocked"`), or makes a new connection after `dropped`;
  - then asks for the watch again.
  - A replacement that cannot be made fails the watch, and the next click tries again.
- The failed move of a hand-over, on a connection left carrying nothing, now lets go of it and tells the tab `dropped`. Before, it was forgotten silently, with the tab never told. A watch closed unanswered on an empty connection now goes through the instance's `letGoOfMedia` the same way, `pull-refused` then `dropped`.
- Logs:
  - `media.blocked`: the watch's fields, the media `connection`, and `why`.
  - `media.replacing` with `blocked` when the connection replaced was blocked.
  - `watch.refused` with `blocked`.
  - From the tab: `watch.blocked`, and `media.replace` with `why`, so a blocked replacement can be told from a failed one.

A decision the brief left open: a pull that returns to a connection while a replacement of it is under way also blocks it. The finished replacement clears the block. A replacement that fails or is abandoned leaves the old connection as the tab's current one, still holding an offer nobody will answer, so the block is correct there, not just harmless.

## Agent Brief

**Category:** bug
**Summary:** A receiving connection left with an offer nobody will answer is replaced before its next pull, so the next watch does not hit the media server's 406.

**Current behavior:**
The media server takes no pull into a session until the browser answers that session's last offer. Closing the pulled track does not change that (`docs/media-server.md`, ticket 67). Three places close a pull that returned with an offer, without sending that offer to the tab, and keep the tab's receiving connection:
- a plain watch whose share ended, or whose tab's socket closed, while the media server made the pull;
- a hand-over's move whose new share ended, or whose watcher's socket closed, while the move's pull was made;
- the sweep after a restart, which force-closes a pull the media server made just as the instance stopped.

Each later pull into that connection gets the 406, so the tab's watches are refused (`pull-refused`, `watch.refused` "the media server failed"). This lasts until every other watch on the connection ends and 66's rule lets it go, or until the connection fails and the tab asks to replace it.

**Desired behavior:**
- When the instance closes (or force-closes) a pull on a tab's receiving connection whose offer the tab has not answered and never will, it records that connection as **blocked**.
  - Only the tab's current receiving connection counts. A pull returning to a connection already replaced, or being replaced, is harmless: that session takes no pull again. Leave that case as it is.
- A blocked connection that carries nothing else is let go of, as now (66's rule). The tab's next watch makes a new connection.
- A blocked connection that still carries watches keeps them playing undisturbed. Replace it lazily, on the tab's next watch, not when it is blocked.
- The tab's next watch on a blocked connection pulls nothing into it, so no 406 is ever asked for. Instead the receiving connection is replaced through the existing replacement machinery: the tab's other watches are carried onto the new connection, and the requested watch ends on the stage, on the new connection. The user's click is not refused.
  - Whether the instance tells the tab to replace first and watch again (a new reason on an existing refusal, or a new change), or begins the replacement itself, is the agent's choice. Pick whichever fits the room client's replacement handling best (it holds watches back during a replacement and counts replacements once `connected` arrives). Update the protocol comments to match.
- Blocked survives a restart and an eviction. The sweep after a restart can block a connection, and the instance can stop again before the tab's next watch.
- Any other state the tab can be in while its connection is blocked keeps working as today: a replacement the tab asks for itself, unwatch, the tab leaving, 64's backoff. A replacement of a blocked connection, for whatever reason, clears the block.
- One log line says a connection was blocked and why (catalogued at the top of the log file). The replacement it later causes is distinguishable in the logs from one the tab asked for because its connection failed.

**Check rather than assume:**
- That a session waiting for an answer still delivers its existing pulled tracks. If it does not on real media, the lazy replacement above is wrong, and the replacement should happen as soon as the connection is blocked. Check it with the real-media run below, and record what you see in `docs/media-server.md`.
- That unwatching a share on a blocked connection (its pull's close) works without an answer. Ticket 67 saw a close go through on such a session; confirm it doesn't hit the 406 or get stuck.
- Whether a pull the media server reported as failed, although it made one (the fake's `fail("pull", { done: true })`), also leaves an offer waiting. If you cannot tell from real media, note it in the docs as not yet seen and leave it alone.

**Key interfaces:**
- `Shares.watch`, `Shares.move` (the hand-over's move of a watch) and the sweep's handling of a half-made pull. These are where a returned pull is closed unanswered today.
- `Shares.replace` / `replaceNext` and the room client's replacement flow. The block reuses them; it is not a second way of carrying watches over.
- The media protocol's changes for a refused watch or replacement (`pull-refused`, `unavailable`, `connected`, `replaced`, `dropped`). Extend them rather than invent a parallel path.
- The fake media server's `oneOfferAtATime()`. It already plays the 406.
